Si no trabajaste este chat, igual puedes usar la carpeta. Lee esto entero.
Este pipeline es independiente del de tickets (pipeline_zarigueya/) y del de Jurídico
(pipeline_juridico/): no comparte código de negocio, catálogos ni columnas con ellos.
Solo el patrón técnico (estructura de carpeta, guardas de seguridad, forma de generar
SQL) es el mismo.


1. QUÉ PROBLEMA RESUELVE
"26e05 Diplomados - Reporte de Ordenes Financieras registradas y pagadas por Periodo
Academico.xlsx" trae 3 hojas, pero solo UNA es fuente real:
  - "26e - Reporte de Ordenes Financ" (420 filas, 82 columnas): 1 fila = 1 orden
    financiera de matrícula a un diplomado.
  - "Asesores" y "Diplomados " son tablas dinámicas de Excel (resúmenes PAGO/NO PAGO
    ya calculados por Excel) — NO son fuente, se ignoran.
Este paquete parte esa hoja en 8 catálogos + un puente a CORE (estudiante_ref) + un
hecho (orden_financiera), sin inventar columnas que el Excel no trae.

A diferencia de Jurídico, este Excel SÍ trae el documento del estudiante (Doc_alum),
así que el cruce con core.person se hace primero por documento (match fuerte) y solo
de respaldo por nombre normalizado — igual mecanismo que tickets.persona_ref.


2. QUÉ ES 01 / 02 / 03 (SQL)
No son "versiones". Son TRES PASOS, en orden:

  01_diplomas_schema.sql
      Crea las 10 tablas dentro de diplomas (el esquema YA EXISTÍA, vacío,
      creado antes de este pipeline, en la misma base "core" de GCP donde vive
      legal_consulting). CREATE ... IF NOT EXISTS: no rompe nada si ya hay algo con
      el mismo nombre.

  02_cargar_catalogos.sql
      UPSERT de catálogos (periodo, diplomado, sede, seccional, modalidad, jornada,
      estado_pago, clasificacion_contable) y el puente a CORE (estudiante_ref).
      Lo GENERA pipeline.py. MODO ACUMULAR (desde sep 2026): no borra nada, código
      existente se actualiza, código nuevo se inserta. Ver punto 6.

  03_cargar_diplomados.sql
      UPSERT de orden_financiera. También lo genera pipeline.py. Si lo corres ANTES
      del 02, falla (faltan los catálogos). MODO ACUMULAR: orden existente se
      actualiza (ej. cambio de estado de pago), orden nueva se inserta, nada se borra.

Orden: siempre 01 → 02 → 03.
Nunca en la base CORE de GCP salvo que el dueño lo autorice (--permitir-prod).
Prueba primero en un Postgres local (por ejemplo, base diplomados_dev).


3. ARCHIVOS DE ESTA CARPETA
  normalizar_diplomados.py         Lee la hoja de origen, limpia y normaliza a CSV/xlsx.
  generar_sql_carga.py             Convierte los CSV en 02 y 03. Lo necesita pipeline.py.
  pipeline.py                      Orquesta: normalizar → generar SQL → cargar opcional → validar.
  01_diplomas_schema.sql  Crear tablas.
  04a_verificar_match_core_person.sql Solo lectura: cruza estudiante_ref contra core.person
                                       (documento primero, nombre de respaldo). No modifica nada.
  requirements.txt                 Dependencias Python.
  .env.example                     Modelo de conexión local. Copiar a .env; NO compartir
                                    el .env con contraseña.
  diplomas.dbml / ERD_diplomas.html   Diagrama del modelo.


4. CÓMO CORRERLO
  python -m pip install -r requirements.txt

  Solo normalizar (no toca ninguna base de datos):
    python normalizar_diplomados.py "RUTA\26e05 Diplomados ....xlsx"

  Normalizar + generar 02 y 03:
    python pipeline.py "RUTA\26e05 Diplomados ....xlsx"

  Cargar a Postgres local (opcional, con .env apuntando a diplomados_dev):
    python pipeline.py "RUTA\26e05 Diplomados ....xlsx" --cargar

  Cargar a CORE/GCP (solo con autorización explícita del dueño de la base):
    python pipeline.py "RUTA\...xlsx" --cargar --permitir-prod

5. LÍMITES CONOCIDOS — REVISAR ANTES DE CARGAR A PRODUCCIÓN

a) advertencias_calidad.csv (se genera junto con los demás CSV, si aplica):
   En la corrida del 2 sep 2026 aparecen 53 advertencias:
     - 52 son teléfonos (Tel_casa/Tel_celular) con longitud distinta a 10 dígitos:
       la mayoría trae el prefijo de país "57" pegado adelante (ej. "573004869007"),
       algunos son basura evidente ("1111111", "0"), otros parecen truncados. Se
       guardan tal cual como texto, sin "arreglarlos" solos.
     - 1 es la orden 728897: llegó del Excel sin diplomado/sede/seccional/modalidad/
       jornada, y las dos columnas que podrían dar una pista (Nomcencos y
       Grupo_facturacion) se contradicen entre sí sobre cuál sería. Se cargó con esos
       campos en NULL (confirmado con el dueño del dato: "queda en blanco"), sin
       adivinar el valor.

b) estudiante_ref.core_person_id siempre queda NULL / match_status 'pendiente' en
   esta primera carga: el cruce contra core.person (solo SELECT, sin FK) es un paso
   manual/posterior con 04a_verificar_match_core_person.sql, igual que en tickets y
   legal_consulting. A diferencia de Jurídico, aquí el match primario es por
   documento (Doc_alum = core.person.document), mucho más confiable que por nombre.

   Corrida del 2 sep 2026 contra la base real: 0 de 418 estudiantes cruzaron, ni por
   documento ni por nombre (se comprobó a mano que ni el primer documento del lote,
   23836213, existe en core.person). core.person sí tiene datos (1755 filas, formato
   compatible: document numérico plano, full_name en mayúsculas) — no es un problema
   de formato ni un bug de esta consulta. Según el dueño de CORE, estos estudiantes
   SÍ deberían estar ahí; se está revisando por qué no aparecen (probable retraso de
   sincronización desde el ERP de origen hacia CORE, dado que el lote es de agosto
   2026, muy reciente). No requiere ningún cambio en este pipeline: cuando CORE se
   actualice, volver a correr 04a_verificar_match_core_person.sql resolverá el cruce
   solo.

c) tipo_documento_origen (columna Tip_identificacion: C/PPT/E/T) se guarda crudo, sin
   traducir a los códigos de core.person.type_document. El mapeo fue confirmado con
   el dueño del dato (C=Cédula de Ciudadanía, PPT=Permiso de Protección Temporal,
   E=Cédula de Extranjería, T=Tarjeta de Identidad) y queda documentado en
   01_diplomas_schema.sql, pero la traducción real se hace al momento
   de cruzar contra CORE, no en la carga.

d) grupo_facturacion_codigo / descripcion_grupo_facturacion se guardan como texto
   informativo en orden_financiera, SIN catálogo ni integridad referencial: se
   comprobó que el mismo código de grupo aparece con diplomados distintos en filas
   distintas del lote (no es una dimensión estable). No cruzar esos códigos como si
   fueran una FK.

e) sistema_origen (columna Documento del Excel) viene constante 'FECO' en las 420
   filas de este lote. Se guarda tal cual (nomenclatura fija del sistema origen,
   confirmado con el dueño del dato); no se modeló como catálogo porque no varía.

f) Nomcencos (nombre del diplomado en el centro de costos) difiere de Nom_unidad en
   4 de los 12 diplomados (espacios extra, "MODALIDAD VIRTUAL" añadido). Se usó
   Nom_unidad como nombre canónico de diplomado.nombre; Nomcencos no se guarda aparte.


6. MODO ACUMULAR (piloto de automatización, sep 2026)

La primera versión de este pipeline (02/03 con TRUNCATE + ids fijos) se reemplazó por
UPSERT: cada catálogo y orden_financiera se identifican por su llave natural (código de
diplomado/sede/etc., documento del estudiante, número de Orden — todas ya son UNIQUE en
01_diplomas_schema.sql). Si la llave ya existe, se ACTUALIZA; si no, se INSERTA. Nunca se
borra nada. Los FK (periodo_id, diplomado_id, etc.) se resuelven con subconsultas por
código, no con ids fijos, así funciona igual en la primera carga que acumulando sobre
datos ya existentes.

Excepción a propósito: el UPSERT de estudiante_ref NUNCA toca core_person_id ni
match_status — esos los llena 04a_verificar_match_core_person.sql / un futuro proceso de
confirmación manual, y si el UPSERT los reescribiera, cada recarga los resetearía a NULL
/ 'pendiente' y se perdería el trabajo de cruce contra CORE.

Se agregó updated_at (además de created_at) a estudiante_ref y orden_financiera, para
saber cuándo se actualizó por última vez cada fila. Si ya tenías el esquema cargado con
la versión anterior, 01_diplomas_schema.sql trae ALTER TABLE ... ADD COLUMN IF NOT EXISTS
para agregar esas columnas sin tocar las filas existentes — hay que volver a correrlo.

Archivos PRUEBA_*.sql: simulan "la próxima carga semanal" (1 orden que ya existe
cambiando de NO PAGO a PAGO + 2 órdenes nuevas con estudiantes ficticios, documento
900000001/900000002, Orden 999001/999002) para validar que el modo acumular funciona
antes de automatizarlo. Correr PRUEBA_02 → PRUEBA_03, revisar, y después PRUEBA_04 para
borrar esos datos ficticios (no toca ninguna fila real del lote de 420).

Además, normalizar_diplomados.py ahora marca cada advertencia con nivel "critico" o
"info" (columna nueva en advertencias_calidad.csv). "critico" = un dato no tiene el tipo
que le corresponde (fecha/monto/documento no parseable) o falta un campo requerido; la
fila se omite y, si se usa pipeline.py --cargar, la carga completa se bloquea sola (pasa
--forzar-carga-con-criticas para saltarte el freno, no recomendado). "info" = formato
raro pero sin problema de tipo (ej. teléfono con 12 dígitos); no bloquea nada.


7. FASE 2 — AUTOMATIZACIÓN (carpeta automatizacion/)

sync_diplomados.py: revisa la carpeta DATOS/diplomados/ en Drive, procesa lo nuevo con
el mismo normalizar_diplomados.py/generar_sql_carga.py de aquí (sin duplicar lógica), y
si no hay advertencias críticas carga a diplomas (UPSERT); si las hay, NO carga nada y
solo notifica por correo. Pensado para correr como Cloud Run Job disparado por Cloud
Scheduler cada lunes 9am. Ver automatizacion/DESPLIEGUE.md para los comandos gcloud
paso a paso (requiere acceso al proyecto de GCP; no se desplegó desde este chat).

diplomas.archivo_procesado (tabla nueva en 01_diplomas_schema.sql) lleva el registro de
qué archivo de Drive ya se cargó, para no reprocesar el mismo dos veces.
